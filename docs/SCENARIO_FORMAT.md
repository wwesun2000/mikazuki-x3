# ScenarioLink 与 SN4Font 静态格式记录

本记录对应本地 ISO 中提取的 `SCENARIO` 目录，证据索引为 `SCENARIO-001`（`analysis/scenario_report.json`）。报告为每个输入文件及每个 ScenarioLink 子块保存 SHA-256。原始提取关系见 `FAD-001`、`ISO-001`。

当前已恢复容器、脚本符号/标签定位、候选文本字节及字体字符映射；尚未恢复完整脚本虚拟机，尚不能把候选文本顺序当成游戏运行顺序。

## 已验证的数据

| 文件 | 子块数 | 标签数 | 文本候选片段数 | 候选字符数 |
|---|---:|---:|---:|---:|
| sn2.sn4 | 5 | 1,988 | 10,308 | 164,242 |
| sn4.sn4 | 5 | 2,989 | 18,651 | 193,142 |
| sn4g.sn4 | 30 | 6,566 | 32,291 | 479,513 |
| 合计 | 40 | 11,543 | 61,250 | 836,897 |

这些是片段和字符的实际静态计数，包含标点、分隔的姓名插入前后文字、重复文本及可能不可达内容，不是完整台词数、唯一翻译量或游戏完成度。

三份 `.spk` 分别含 4、4、29 个 `ScenePack` 子块。当前工具只验证它们的外层容器，不扫描它们的场景指令作为台词。

## ScenarioLink 外层容器

观察到全部六份 `.sn4` / `.spk` 使用同一外层结构，整数均为 little-endian：

| 偏移 | 字段 |
|---|---|
| `0x00`，16 字节 | `ScenarioLink`，NUL 填充 |
| `0x10`，16 字节 | `:Ver:3.25.2.157`，NUL 结尾 |
| `0x20` / `0x60` | `top00_0000` 字符串，各位于 64 字节区域；字段用途尚未验证 |
| `0xA0` | `uint32` 子块数 N |
| `0xA4` | N 个 `(uint32 offset, uint32 size)` |

所有子块恰好连续覆盖目录后到文件结尾的区域，无外层压缩包装或未解释尾部。`.sn4` 内每块以 `SCR-file:Ver:3.25.2.157` 开头，`.spk` 内每块以 `ScenePack` 及对应版本开头。“外层直存”不意味着所有子块内的资源格式都已解码。

解析器在重复/重叠块、越界、未识别版本、尾部剩余字节时失败，不推测新的格式。

## SCR-file 子块

下面的偏移相对子块起点：

| 偏移 | 已观察结构 |
|---|---|
| `0x00` | `SCR-file:Ver:3.25.2.157` |
| `0x30` 至 `0x42F` | 256 个 `uint32`；非零项全部落在符号记录边界，疑似散列表桶 |
| `0x430` | 代码区开始偏移 |
| `0x434` 至代码区 | 4 字节对齐的变长符号记录 |

符号记录为 `(uint16 link_delta, uint16 tag, uint32 code_relative_offset, ASCII name, NUL, padding)`。`link_delta` 在本构建中总是零或本记录的对齐长度；具体散列算法和链表语义尚未执行验证。

观察到两类 tag：

- `0x6F4E`：标签。全部 11,543 条记录都通过两个独立字节条件校验：`code_offset + code_relative_offset` 指向 `0x22`；该位置之前的 NUL 结尾名字与表中名字一致。
- `0xFFFF`：符号用途尚不确定。保留原值与目标地址，不标注为变量或分支。

已校验的标签锚点周围格式为：`85 length block_selector ASCII_name 00 22`，其中 `length = len(ASCII_name) + 2`。`block_selector` 的运行语义仍待确认。文本记录附带其最近的前置标签，这只是文件布局关系，不证明执行会到达此处。

## 文本与控制字节

无需 OCR 或字体反查即可从代码区读取大量合法 CP932（Windows Shift-JIS）日文。候选形式为 `02 <CP932 bytes> 03`。当前工具仅提取没有内嵌 C0 控制字节、长度 1–4096 字节、严格 CP932 可解码的片段；全角空格、标点和原始字节全部保留。

每条 JSONL 记录含：源文件 SHA-256、子块编号/起点、文件绝对字节偏移、片段原始 hex、UTF-8 文本、分隔符位置、前后 12 字节上下文、前置标签，以及 `candidate-static-not-vm-validated` 状态。

已观察 `03 0D 02` 夹在“我的名字是……”与句号之间等情形，说明姓名或其他控制操作可能位于文本片段之间。`0x04` 常见于片段间。它们的名称插入、换行、等待等具体语义尚未验证，不能直接删除或把这些片段机械拼接成最终台词。

当前没有识别完整指令边界，因此不能保证每个 `02` 都是文本操作码，也不能保证没有其他文本承载方式。导出的候选必须先与 VM 和运行画面对齐，才能进入可发布翻译包。翻译应保留源码稳定 ID，标明控制占位符、场景上下文和分支；整体校对完成后再开放发布门槛。

## SN4Font

三份字体文件分别有 10 / 22 / 21 个字体组、2,869 / 4,342 / 3,430 条字形记录。所有记录的 CP932 码均严格解码成功。

| 偏移 | 观察到的结构 |
|---|---|
| `0x00`，16 字节 | `SN4Font:V.1.4.0` + NUL |
| `0x10`、`0x14` | 两个未解释 `uint32`，本构建为 33、23 |
| `0x18` | 字体组数 |
| `0x1C` | 首个组描述符 |

每个组描述符为 5 个 `uint32`：`family_id`、推测的字号、payload 格式标识（当前均为 3）、字形数、下一个描述符偏移。之后每个字形占 12 字节：CP932 代码、4 个尚未解释的度量字节、字形 payload 偏移。代码以 little-endian 整数保存，例如整数 `0x8141` 对应 CP932 字节 `81 41`。

各组描述符连续排列，末组 next 为零；首个字形 payload 紧跟所有描述符及记录。全部 payload 指针严格递增、位于文件内，因此工具可保存每个字形的原始字节范围。字形像素压缩与度量尚未解码；保留这些资料可用于后续还原原版字形。现代渲染可使用 Unicode 字体，但仍需保留原版布局、强调、特殊字形等内容。

`namkan.txt` 也可严格解码为 CP932，内容呈日文字符表；“姓名输入字符表”仅为结合内容和文件名作出的推断。

## 输出与验证

运行：

```powershell
python tools/scenario.py
python -m unittest discover -s tests -p test_scenario.py -v
```

- `analysis/scenario_report.json`：计数、子块范围、源身份、限制。
- `local/scenario/text_candidates.jsonl`：全部 61,250 个候选片段，约 41 MB；仅用于本地分析。
- `local/scenario/symbols.jsonl`：完整符号表及经校验的标签锚点。
- `local/scenario/font_map.json`：全部字体分组、字符码、字形范围。
- `local/scenario/namkan.utf8.txt`：字符表的无损 UTF-8 文本转换。

10 项格式/边界/映射单元测试通过。另外对实际导出的 61,250 条记录逐条从源 `.sn4` 复读，确认 raw hex、前后的 `02`/`03` 以及 CP932→Unicode 内容完全一致。该验证保证提取证据与源字节一致，不等同于 VM 行为或剧情覆盖验证。

下一步应从游戏 ELF 中定位 ScenePack/SCR 的加载、分派、文本显示、标签跳转与存档逻辑，结合受控运行逐个确定指令长度和状态语义。保留未知指令并阻止静默跳过，才能满足原作内容完整保留和可靠存档要求。
